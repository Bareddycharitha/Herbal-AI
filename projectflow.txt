============================================================
              HERBAL-AI — PROJECT DEVELOPMENT FLOW
============================================================

This document explains how Herbal-AI was developed from the
initial idea to the final production deployment.

The project was developed in multiple stages, starting from
individual machine learning models and gradually building the
backend, frontend, AI features, MLOps pipeline, Docker
containers, CI/CD workflow and AWS deployment.


============================================================
PHASE 1 — PROJECT IDEA AND PLANNING
============================================================

The initial idea was to build an AI-powered platform that
could combine skin disease analysis and medicinal plant
identification in a single application.

The main goals were:

1. Skin disease image classification
2. Medicinal plant identification
3. AI-assisted medical information
4. Herbal recommendations
5. Explainable AI
6. User authentication
7. Prediction history
8. AI chatbot
9. PDF report generation
10. MLOps and model management
11. Cloud deployment

Instead of building only a machine learning model, the goal
was to create a complete end-to-end AI application.

The project was therefore divided into multiple components:

- Dataset preparation
- Model development
- Model evaluation
- Inference pipeline
- Knowledge base
- Recommendation system
- Explainability
- Backend API
- Frontend
- Authentication
- Database
- LLM integration
- MLOps
- Docker
- CI/CD
- AWS deployment


============================================================
PHASE 2 — DATASET COLLECTION AND PREPARATION
============================================================

The next step was collecting and organizing the datasets
required for the AI models.

The project required datasets for three major purposes:

1. Skin disease classification
2. Medicinal plant classification
3. Universal image classification

The datasets were organized into separate directories so that
they could be used independently during training.

Skin disease data was organized into disease-specific classes.

The medicinal plant dataset was organized into plant classes.

An additional Other/negative dataset was used for the universal
image classification problem.

The dataset structure was designed so that the training,
validation and test sets could be handled separately.


============================================================
PHASE 3 — SKIN DISEASE MODEL DEVELOPMENT
============================================================

After preparing the datasets, the first major AI component
was the skin disease classifier.

The skin disease model was developed using:

- PyTorch
- timm
- EfficientNetV2-S

The model was configured to classify 22 skin disease/condition
categories.

The development process included:

1. Dataset loading
2. Image preprocessing
3. Image transformations
4. Train/validation/test split
5. Model creation
6. Transfer learning
7. Training
8. Validation
9. Checkpoint saving
10. Evaluation
11. Classification report
12. Confusion matrix
13. Inference testing


The trained model checkpoint was saved and later integrated
into the backend inference pipeline.


============================================================

After the skin model, a separate model was developed for

The herb classifier also uses:

The development process included:

1. Dataset organization

============================================================
PHASE 5 — UNIVERSAL IMAGE CLASSIFIER
============================================================

After developing the specialized models, a major problem had
to be addressed.

If a user uploads an inappropriate image, the system should
not blindly send that image to the skin or herb model.

For example:

A plant image should not be directly processed by the skin
disease classifier.

A skin image should not be directly processed by the herb
classifier.

To solve this, a Universal Image Classifier was developed.

Architecture:

EfficientNetV2-S


Classes:

0 -> Skin
1 -> Medicinal
2 -> Other


The universal classifier became the first AI decision layer.

The final routing became:

                Uploaded Image
                      |
                      v
              Universal Classifier
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
        Skin      Medicinal     Other
          |           |
          v           v
     Skin Model    Herb Model


This created a multi-model AI pipeline instead of using one
model for every type of image.


============================================================
PHASE 6 — INFERENCE PIPELINE
============================================================

After the individual models were working, the next step was
building the inference system.

The inference pipeline was responsible for:

- Loading trained checkpoints
- Preprocessing uploaded images
- Running model inference
- Converting model outputs to probabilities
- Mapping class indexes to class names
- Returning confidence values
- Returning top predictions
- Handling model errors


Separate inference modules were created for:

- Universal classifier
- Skin classifier
- Herb classifier


The inference system was then connected to the backend.


============================================================
PHASE 7 — OUT-OF-DISTRIBUTION DETECTION
============================================================

During testing, it became clear that classification confidence
alone is not enough.

A neural network can sometimes produce a high confidence
prediction even for an image that is not really part of its
expected data distribution.

Therefore, an OOD detection layer was added.

The system calculates:

1. Energy score
2. Maximum Softmax Probability
3. Prediction entropy
4. Combined OOD score


These signals are used to identify potentially inappropriate
inputs.

The goal was to make the application more robust instead of
simply trusting the highest probability class.


============================================================
PHASE 8 — KNOWLEDGE BASE
============================================================

Once model predictions were working, the next problem was:

A prediction alone is not very useful to the user.

For example:

"Eczema — 80%"

does not provide enough information.

Therefore, structured knowledge bases were created.

The disease knowledge base contains information such as:

- Description
- Symptoms
- Causes
- Prevention
- Risk factors
- When to consult a doctor
- Medical disclaimer


The herbal knowledge base contains information such as:

- Common name
- Botanical name
- Benefits
- Traditional uses
- Preparation methods
- Side effects
- Contraindications
- Evidence level


Disease-to-herb mappings were also created.

The architecture became:

Model Prediction
       |
       v
Knowledge Base
       |
       +---- Disease Information
       |
       +---- Herbal Information
       |
       +---- Recommendations


This kept the machine learning model separate from the
supporting domain knowledge.


============================================================
PHASE 9 — HERBAL RECOMMENDATION ENGINE
============================================================

The next stage was connecting predictions with relevant
herbal information.

The recommendation engine takes the model prediction and
uses the knowledge base to find related herbs.

The system can then provide:

- Recommended herb
- Botanical information
- Benefits
- Traditional uses
- Preparation information
- Precautions
- Evidence information


An important part of this stage was ensuring that herbal
recommendations were not simply invented by the language model.

The structured knowledge base provides the underlying
information.


============================================================
PHASE 10 — EXPLAINABLE AI WITH GRAD-CAM
============================================================

After the prediction pipeline was working, explainability
was added.

The problem was:

A user can see a prediction, but cannot see what part of the
image influenced the model.

To address this, Grad-CAM was implemented.

Grad-CAM generates a heatmap showing important regions of
the input image.

The workflow became:

Image
  |
  v
Model Prediction
  |
  v
Grad-CAM
  |
  v
Attention / Heatmap
  |
  v
User


This makes the AI prediction easier to inspect and understand.

============================================================
PHASE 16 — LLM INTEGRATION
============================================================

After the traditional ML pipeline was stable, Generative AI
features were added.

The initial goal was to allow the system to generate
user-friendly explanations of predictions.

The current architecture uses:

OpenRouter


The prediction context is sent to the LLM layer.

The context can include:

- Predicted condition
- Confidence
- Disease information
- Herbal information


The LLM generates an AI-assisted summary.

A fallback mechanism was also implemented.

If the external LLM service fails or times out, the backend
returns a deterministic fallback response rather than
breaking the application.


============================================================
PHASE 17 — AI CHATBOT
============================================================

After AI summaries were implemented, conversational interaction
was added.

The chatbot receives the current prediction context.

Users can ask questions such as:

- Explain this disease

- Are the recommended herbs safe?
- How long does recovery usually take?
- Can this condition spread?


The chatbot uses the LLM through OpenRouter.

The chatbot is contextual rather than completely generic
because the current prediction information is included in

PHASE 32 — PRODUCTION MODEL ISSUE AND DEBUGGING
============================================================

During production deployment, an important issue was
discovered.

The application could start successfully, but the production
container did not initially contain the trained model
checkpoints required for inference.

As a result, the backend could run while the actual trained
models were not available inside the production container.

The issue was diagnosed by checking the production container
and model loading logs.

The trained model checkpoints were verified on the EC2
environment.

The Docker production image was then rebuilt with the required
trained model checkpoints.

The model files were verified inside the resulting Docker
image.

This confirmed that the production container contained the
actual trained models rather than only the model architecture.


============================================================
PHASE 33 — PRODUCTION DATASET RECOVERY
============================================================

Another production issue occurred with the skin disease
dataset required by the runtime class mapping.

The production environment did not initially contain the
required SkinDisease dataset.

DVC was used to recover the dataset from the configured
remote.

The dataset was pulled into the EC2 environment.

The class mapping was then verified.

The production container was checked to confirm that the
correct 22 skin disease classes were available.

This fixed the issue where predictions could otherwise appear
as generic labels such as:

Class_17


After verification, the correct mapping was restored:

Unknown_Normal -> 17


The production prediction then correctly returned:

Eczema

instead of an incorrect generic class label.


============================================================
PHASE 34 — CORS DEBUGGING
============================================================

During production testing, browser requests initially failed
because the frontend origin and backend CORS configuration
did not match.

The production frontend was running from the current EC2
public IP.

The backend was still configured with the previous frontend
origin.

The CORS configuration was updated to the correct production
frontend origin.

The backend was restarted.

After the change, browser preflight requests returned
successfully and the frontend could communicate with the
backend.

============================================================
PHASE 36 — FRONTEND PRODUCTION CHAT DEBUGGING
============================================================

After the production deployment, the prediction-page AI chat
was tested.

The browser showed an error related to:

crypto.randomUUID()


The issue was not with the AI model or backend.

The frontend message ID generation depended directly on
crypto.randomUUID().

A safer message ID generation helper was added.

The helper uses randomUUID when available and provides a
fallback using crypto.getRandomValues.

The frontend was then rebuilt and redeployed.
